# ADR-01 — Використання Mermaid Flowchart для Activity Diagram

## Статус

Прийнято.

## Контекст

У Завданні №4 потрібно деталізувати UC-04 Оформити замовлення, який було визначено в Завданні №2 та розглянуто з погляду взаємодії учасників у Завданні №3. Необхідно обрати нотацію, яка дозволить на одній діаграмі відобразити основний та альтернативні сценарії, послідовність дій, умовні розгалуження, паралельні процеси, цикли та обмін повідомленнями між учасниками.

## Розглянуті варіанти

### Варіант 1 — Activity Diagram у Mermaid Flowchart

**Переваги:**
- Зручне редагування текстового коду.
- Підтримка розгалужень, циклів та умовного представлення Fork/Join.
- Можливість відображення діаграми безпосередньо в GitHub.
- Наявність опита роботи з ним
- Зручне відстеження змін через Git.

**Недоліки:**
- Fork/Join, Send Signal та Accept Event відображаються умовними позначеннями, а не спеціалізованими UML-елементами.
- Великі діаграми можуть потребувати додаткового налаштування графічного представлення.

### Варіант 2 — Activity Diagram у PlantUML

**Переваги:**
- Підтримка спеціалізованого синтаксису Activity Diagram.
- Зручне моделювання паралельних процесів та розгалужень.
- Можливість розподілу дій за учасниками.

**Недоліки:**
- Потребує додаткових засобів для графічного рендерингу в GitHub.
- Необхідно опанувати інший синтаксис.

### Варіант 3 — BPMN у bpmn.io

**Переваги:**
- Спеціалізована нотація моделювання бізнес-процесів.
- Підтримка потоків повідомлень, подій, пулів та розгалужень.

**Недоліки:**
- Складніше переглядати зміни BPMN XML у Git.
- Потрібне окреме графічне представлення для зручного перегляду в GitHub.

### Варіант 4 — BPMN у Camunda Modeler

**Переваги:**
- Зручний графічний редактор бізнес-процесів.
- Підтримка BPMN 2.0 та різних типів подій.

**Недоліки:**
- Необхідно використовувати окремий редактор.
- Для поточного завдання можливості інструмента є ширшими, ніж потрібно.

### Варіант 5 — Машина станів у Mermaid stateDiagram-v2

**Переваги:**
- Зручне моделювання станів та переходів між ними.
- Підтримка графічного відображення в GitHub.

**Недоліки:**
- Менш зручна для відображення детальної послідовності операцій між різними учасниками.
- Основний акцент робиться на станах об'єкта, а не на виконанні процесу.

## Прийняте рішення

Для Завдання №4 я обрала Activity Diagram у Mermaid Flowchart. На одній діаграмі об'єднала всі чотири сценарії UC-04, які раніше були представлені окремими Sequence Diagram.

Вихідний код діаграми зберігається у файлі .mmd, а графічне представлення та опис — у файлі .md.

## Причини вибору

- Mermaid вже використовувався в попередніх завданнях.
- Activity Diagram підходить для деталізації поведінки UC-04.
- Можна відобразити всі необхідні розгалуження, цикли та паралельні операції.
- Зберігається єдиний підхід до оформлення документації проєкту.
- Діаграму можна переглядати безпосередньо в GitHub.

## Наслідки рішення

**Позитивні:**
- Усі чотири сценарії UC-04 об'єднано в одну модель процесу.
- Зміни діаграми можна відстежувати через коміти.
- Не потрібно створювати окремі PNG-зображення.
- Збережено сумісність із підходом попередніх завдань.

**Негативні:**
- Через велику кількість операцій діаграма має значний розмір.
- Потрібно додатково перевіряти читабельність графічного рендеру.
- Необхідно підтримувати однаковий Mermaid-код у файлах .mmd та .md.
- Семантика Fork/Join та повідомлень задається умовними позначеннями.
