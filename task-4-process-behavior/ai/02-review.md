# Огляд 02 — Вибір типу діаграми для завдання 4

## Пов'язаний промпт

`ai/02-prompt.md`

## Мета перевірки

Оцінити запропоновані способи побудови діаграм та визначити найбільш придатний варіант для моделювання UC-04 Оформлення замовлення в межах проєкту Онлайн-магазин друкованих книг.

## Аналіз результату

За допомогою ШІ я розглянула три типи діаграм та п'ять варіантів їх реалізації. Для порівняння врахувала вимоги до послідовності дій, розгалужень, паралельних процесів, обміну повідомленнями та зручності роботи з GitHub.

| Варіант | Складність | Читабельність | Розгалуження | Паралельні процеси | Обмін повідомленнями | GitHub | Відповідність завданню 4 та UC-04 |
|---|---|---|---|---|---|---|---|
| Activity — Mermaid flowchart | Низька | Висока для невеликих процесів | Ромби та підписані переходи | Явно позначені Fork/Join і паралельні гілки | Умовні підписані стрілки між групами учасників | Нативне відображення в Markdown | Висока за умови явного позначення необхідних конструкцій |
| Activity — PlantUML activity | Середня | Висока | `if/else`, `switch` | `fork`, `fork again`, `end fork` | Дії надсилання й отримання сигналів, доріжки учасників | Код `.puml`; для перегляду потрібен рендер або зображення | Висока, формалізований опис процесу |
| BPMN — bpmn.io | Середня | Висока за знання BPMN | Exclusive Gateway | Parallel Gateway | Message Flow між окремими пулами | Файл `.bpmn` та SVG для перегляду | Висока, добре описує взаємодію учасників |

| Машина станів — Mermaid stateDiagram-v2 | Низька або середня | Висока для життєвого циклу об'єкта | Choice | Fork/Join, паралельні стани | Події та підписи переходів, без окремих потоків повідомлень | Нативне відображення в Markdown | Середня для UC-04: краще описує стани замовлення, ніж послідовність дій |

| Варіант | Переваги | Недоліки |
|---|---|---|
| Mermaid flowchart | Простий синтаксис, швидке редагування, зручна інтеграція з GitHub, знайомий інструмент | Не є повноцінною UML Activity-нотацією; семантику паралельності та повідомлень потрібно позначати явно |
| PlantUML activity | Формалізовані розгалуження, паралельність, доріжки та сигнали | Потребує освоєння синтаксису та додаткового рендерингу для перегляду на GitHub |
| bpmn.io | Візуальний вебредактор, стандартна BPMN-нотація, зручне відображення взаємодії | Потрібно освоїти BPMN; XML менш зручний для ручного аналізу змін |
| Camunda Modeler | Повноцінний BPMN-редактор, підтримка складних процесів та можливість їх подальшої автоматизації | Додаткове встановлення для Desktop Modeler; частина можливостей надлишкова для завдання |
| Mermaid stateDiagram-v2 | Простий опис станів, переходів і життєвого циклу замовлення, GitHub | Менш наочний опис послідовності дій різних учасників і обміну повідомленнями |

Для UC-04 важливо відобразити введення контактних даних, перевірку кількості та наявності книг, створення замовлення або повідомлення покупця про помилку. Activity дозволяє описати ці дії в межах єдиного процесу. Незалежні перевірки можна представити паралельними гілками, якщо така поведінка узгоджується з попередніми вимогами та Sequence Diagram.

## Оцінка результату

Після аналізу запропонованих варіантів я самостійно обрала Activity — Mermaid flowchart. Я вже маю досвід роботи з Mermaid під час виконання попередніх завдань, звикла до його синтаксису, і цей інструмент добре себе зарекомендував. Також у мене вже активована пробна підписка на 7 днів, що стало додатковою перевагою під час вибору. Як альтернативу я розглядала PlantUML activity, оскільки він має більш формалізовані конструкції для розгалужень і паралельних процесів. Проте попередній позитивний досвід роботи з Mermaid, наявність пробної підписки, простота редагування та можливість відображення діаграми безпосередньо в GitHub переважили переваги PlantUML. BPMN також є придатним для моделювання UC-04, особливо для обміну повідомленнями між учасниками. Однак для цього завдання я вважаю Activity більш зручним способом відображення послідовності дій та альтернативних сценаріїв оформлення замовлення. Машина станів була б більш доречною для опису життєвого циклу вже створеного замовлення. Водночас я врахувала обмеження Mermaid flowchart: паралельні гілки та їх синхронізацію потрібно позначити явно, а повідомлення між учасниками представити підписаними стрілками. Остаточну відповідність діаграми вимогам викладача перевірю за оригінальними умовами завдання та матеріалами попередніх робіт. Пробна підписка є додатковим фактором зручності, а не технічною вимогою для відображення Mermaid у GitHub.

## Статус

Наступний етап — побудова діаграми та перевірка її відповідності UC-04 і вимогам викладача.
