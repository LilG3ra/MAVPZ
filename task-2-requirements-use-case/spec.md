# Специфікація — Вимоги та Use Cases онлайн-книжкового магазину

## 1. Мета

Описати функціональні та нефункціональні вимоги до онлайн-магазину друкованих книг, визначити основні сценарії використання, створити Use Case-діаграму та описати оформлення замовлення у форматі Gherkin. Також підготувати вимоги EARS, NFR і матрицю трасування. Усі документи повинні відповідати ER-моделі із Завдання №1.

## 2. Опис предметної області

Система призначена для онлайн-продажу друкованих книг. Покупець може переглядати каталог, шукати книги, отримувати інформацію про авторів, жанри та видання, а також оформлювати замовлення без обов'язкової реєстрації.

Одна книга може мати декілька видань із різними ISBN, видавництвами, цінами та залишками. Замовлення повинно містити хоча б одну позицію, кожна з яких пов'язана з конкретним виданням. Кількість замовлених примірників не може перевищувати доступний залишок.

## 3. Основні сценарії використання

У системі передбачено двох акторів: покупця та працівника магазину.

**Покупець:**

- UC-01 — Переглянути каталог книг.
- UC-02 — Знайти книгу.
- UC-03 — Переглянути інформацію про книгу та видання.
- UC-04 — Оформити замовлення.

**Працівник магазину:**

- UC-05 — Опрацювати замовлення.

Працівник може переглядати оформлені замовлення та змінювати їхній статус на «Опрацьовано».

## 4. Зв'язки та бізнес-правила

- Покупець може оформити замовлення без реєстрації.
- Замовлення повинно містити щонайменше одну позицію.
- Кожна позиція замовлення пов'язана з конкретним `EDITION`.
- Кількість замовлених примірників повинна бути більшою за нуль.
- Перед створенням замовлення система обов'язково перевіряє доступний залишок кожного видання.
- Якщо примірників недостатньо, замовлення не створюється.
- Під час оформлення замовлення перевіряються обов'язкові контактні дані покупця.
- Ціна видання фіксується на момент оформлення замовлення.
- UC-04 включає перевірку наявності примірників через зв'язок `include`.
- Для UC-04 описано чотири Gherkin-сценарії: успішне оформлення, недостатній залишок, недопустима кількість та відсутність контактних даних.

## 5. Критерії прийняття

**Критерій №1:** Створено читабельну Use Case-діаграму з двома акторами, п'ятьма основними сценаріями, межею системи та обґрунтованими зв'язками.

**Критерій №2:** Для UC-04 підготовлено чотири Gherkin-сценарії у форматі Given / When / Then, включно з успішним та помилковими випадками.

**Критерій №3:** Функціональні вимоги FR-01–FR-18 сформульовані у форматі EARS та мають унікальні ідентифікатори.

**Критерій №4:** Описано сім нефункціональних вимог NFR-01–NFR-07 із числовими межами та способами перевірки.

**Критерій №5:** Створено матрицю трасування, яка пов'язує функціональні вимоги з Use Cases та відповідними Gherkin-сценаріями.

**Критерій №6:** Модель відповідає восьми сутностям Завдання №1: BOOK, AUTHOR, GENRE, EDITION, PUBLISHER, USER, ORDER, ORDER_ITEM.

**Критерій №7:** Підготовлено README, CHECKLIST, ADR, DEFENSE та документацію роботи з ШІ у папці `ai/`.

## 6. Обмеження (Out of Scope)

У межах завдання розглядаються вимоги та сценарії використання, а не реалізація готового застосунку. Фізична база даних, повноцінна авторизація, інтеграція онлайн-оплати та поштових служб не входять до поточної роботи. Основні бізнес-правила залишаються узгодженими з ER-моделлю першого завдання.
