# ADR-01 — Вибір предметної області та структури моделі

## Статус
Прийнято.

## Контекст
Для першої лабораторної роботи потрібно було обрати предметну область та створити її ER-модель. Я вирішила розробляти інформаційну систему онлайн-магазину друкованих книг. Спочатку планувалося передбачити каталог, пошук книжок, роботу з користувачами, оформлення замовлень, оплату, доставку та контроль складських залишків. Після аналізу вимог до лабораторної роботи я вирішила спростити предметну область, залишивши лише основні сутності та зв'язки.

## Розглянуті варіанти
### Варіант 1 — Деталізована модель
Створити окремі сутності для оплати, доставки, складського обліку та інших процесів.

**Переваги:**
- Детальніший опис роботи магазину.
- Більше можливостей для розвитку системи.

**Недоліки:**
- Значна кількість сутностей і зв'язків.
- Складніша діаграма.
- Надлишкова деталізація для першого завдання.

### Варіант 2 — Спрощена модель
Залишити основні сутності, а інформацію про оплату, доставку та складські залишки представити їхніми атрибутами.

**Переваги:**
- Простіша структура.
- Зрозуміліша діаграма.
- Легше перевіряти зв'язки та кардинальності.
- Можливість поступово розширювати систему.

**Недоліки:**
- Частина процесів представлена лише загально.
- Для повноцінної реалізації знадобиться деталізація моделі.

## Прийняте рішення
Я обрала спрощену модель онлайн-магазину друкованих книг із восьми сутностей:
- BOOK — книга;
- AUTHOR — автор;
- GENRE — жанр;
- EDITION — видання;
- PUBLISHER — видавництво;
- USER — користувач;
- ORDER — замовлення;
- ORDER_ITEM — позиція замовлення.

## Причини вибору
- Відповідність вимогам першої лабораторної роботи.
- Бажання уникнути зайвої складності.
- Зрозумілість структури предметної області.
- Можливість використовувати модель у наступних завданнях.

## Наслідки рішення

**Позитивні:**
- Модель містить необхідні сутності.
- Діаграму простіше читати та перевіряти.
- Залишається можливість подальшого розвитку системи.

**Негативні:**
- Оплата, доставка та складський облік представлені спрощено.
- Для створення повноцінного застосунку модель доведеться розширювати.
- Частину бізнес-правил потрібно описувати окремо.
